# Collecteur vocal Discord (préparatoire)

Le noyau `src/lib/discord-voice-gateway.ts` utilise le WebSocket natif de Node, les heartbeats, les séquences Gateway et `RESUME`. Il écoute uniquement `GUILD_VOICE_STATES` avec `GUILDS`; il n'active pas `GUILD_PRESENCES` ni `GUILD_MEMBERS`. La connexion initiale récupère l'URL recommandée auprès de `/gateway/bot`.

La configuration utilise `VOICE_PRESENCE_ENABLED` (seule la valeur exacte `true` active), `VOICE_PRESENCE_GUILD_ID`, `VOICE_PRESENCE_CHANNEL_IDS` et `VOICE_PRESENCE_SESSION_ID`, avec le `DISCORD_BOT_TOKEN` existant. Le collecteur intégré refuse de démarrer si la soirée n'est pas explicitement associée à une seule session.

À la première synchronisation, les membres déjà présents commencent à l'heure de l'observation et les intervalles sont marqués `partial`. Une reprise valide rejoue les événements après le dernier numéro de séquence. Une session invalide ou un numéro de séquence inutilisable détruit l'état en mémoire et signale une lacune; aucune durée manquante n'est estimée. Une réponse HTTP 401/403 à la découverte Gateway arrête le collecteur et signale une erreur fatale sans le jeton; les erreurs réseau et autres statuts HTTP restent réessayés avec délai exponentiel plafonné. Les codes de fermeture indiquant une configuration ou une authentification invalide arrêtent aussi les tentatives et remontent leur code sans le jeton. Le callback requis `onFatal` distingue une erreur HTTP de découverte d'une fermeture Gateway définitive; `start()` retourne après la première tentative, tandis que les erreurs transitoires continuent en arrière-plan, donc l'hôte doit superviser ces callbacks. Les arrêts SIGINT/SIGTERM ferment la socket et signalent une lacune pour les visites encore ouvertes.

Le pont GameNight convertit un intervalle en secondes et l'associe à la session configurée seulement si la communauté, le guild Discord, le salon VOICE actif, l'état `SCHEDULED`, la date de début et l'invitation active/créateur correspondent. Les lignes idempotentes conservent l'utilisateur GameNight, le salon, l'heure de début, la durée et l'indicateur partiel. Seul le créateur de la soirée peut voir les totaux; l'accès passe aussi par `getSessionAccessRole`. La migration est additive et n'a été appliquée à aucune base distante.

La configuration d'exemple laisse le flag vide, donc désactivé. N'active pas la collecte avant décision sur les salons, le consentement et la rétention/suppression : le modèle ne fixe pas encore de durée de conservation. Aucun hôte durable ni démarrage réel n'a été configuré. Une erreur de découverte Gateway est retentée avec délai exponentiel plafonné; les tests utilisent seulement des membres et sockets synthétiques. Le pont requiert un callback d'erreur et `stop()` attend les écritures déjà lancées. Avant l'upsert, une transaction revalide et verrouille dans un ordre stable l'utilisateur, la session `SCHEDULED` et sa date, la communauté ACTIVE et son guild, la configuration VOICE active, l'invitation ACTIVE si nécessaire, puis l'appartenance quand l'isolation est activée. Les révocations ou désactivations qui gagnent cette course empêchent l'écriture; le mode isolation OFF conserve le chemin d'accès actuel sans exiger de membership.

Les intervalles ne sont écrits qu'à leur fermeture et seuls les états `SCHEDULED` sont acceptés. Le verrou sur la session sérialise l'upsert avec sa transition vers `DONE` : une écriture déjà validée termine avant la clôture, tandis qu'un intervalle traité après le commit de clôture est rejeté. La règle produit sur la présence qui se prolonge après la session reste à arbitrer avant activation.
