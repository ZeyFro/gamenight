# Collecteur vocal Discord (préparatoire)

Le noyau `src/lib/discord-voice-gateway.ts` utilise le WebSocket natif de Node, les heartbeats, les séquences Gateway et `RESUME`. Il écoute uniquement `GUILD_VOICE_STATES` avec `GUILDS`; il n'active pas `GUILD_PRESENCES` ni `GUILD_MEMBERS`. La connexion initiale récupère l'URL recommandée auprès de `/gateway/bot`.

La configuration utilise `VOICE_PRESENCE_ENABLED` (seule la valeur exacte `true` active), `VOICE_PRESENCE_GUILD_ID`, `VOICE_PRESENCE_CHANNEL_IDS` et `VOICE_PRESENCE_SESSION_ID`, avec le `DISCORD_BOT_TOKEN` existant. Le collecteur intégré refuse de démarrer si la soirée n'est pas explicitement associée à une seule session.

À la première synchronisation, les membres déjà présents commencent à l'heure de l'observation et les intervalles sont marqués `partial`. Une reprise valide rejoue les événements après le dernier numéro de séquence. Une session invalide ou un numéro de séquence inutilisable détruit l'état en mémoire et signale une lacune; aucune durée manquante n'est estimée. Les codes de fermeture indiquant une configuration ou une authentification invalide arrêtent les tentatives et remontent le code sans le jeton. Les arrêts SIGINT/SIGTERM ferment la socket et signalent une lacune pour les visites encore ouvertes.

Le pont GameNight convertit un intervalle en secondes et l'associe à la session configurée seulement si la communauté, le guild Discord, le salon VOICE actif, l'état `SCHEDULED`, la date de début et l'invitation active/créateur correspondent. Les lignes idempotentes conservent l'utilisateur GameNight, le salon, l'heure de début, la durée et l'indicateur partiel. Seul le créateur de la soirée peut voir les totaux; l'accès passe aussi par `getSessionAccessRole`. La migration est additive et n'a été appliquée à aucune base distante.

La configuration d'exemple laisse le flag vide, donc désactivé. N'active pas la collecte avant décision sur les salons, le consentement et la rétention/suppression : le modèle ne fixe pas encore de durée de conservation. Aucun hôte durable ni démarrage réel n'a été configuré. Une erreur de découverte Gateway est retentée avec délai exponentiel plafonné; les tests utilisent seulement des membres et sockets synthétiques. Le pont requiert un callback d'erreur et `stop()` attend les écritures déjà lancées. La vérification des droits et l'upsert ne sont pas atomiques : avant activation, il faudra décider si une transaction isolable est requise pour fermer la course de révocation.
